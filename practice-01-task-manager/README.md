# Практическая работа №1 — Task Manager

Веб-приложение на Django для управления личными задачами. Пользователь может зарегистрироваться, войти, создать задачу, изменить срок и приоритет, отметить её выполненной, вернуть в работу и удалить после подтверждения. Все операции с задачами ограничены владельцем объекта.

## Возможности

- регистрация, вход и безопасный выход методом POST;
- личный список задач для каждого пользователя;
- название, описание, срок, приоритет и состояние задачи;
- сначала активные задачи, затем выполненные; внутри групп — высокий, обычный и низкий приоритет, ближайший срок и задачи без срока;
- визуальное обозначение приоритета, состояния и просрочки;
- адаптивный интерфейс Bootstrap 4;
- защита CSRF и ответ 404 при обращении к чужой или отсутствующей задаче;
- автоматические тесты обязательных сценариев.

## Быстрый запуск через Docker

Нужны Docker и Docker Compose.

```bash
docker compose up -d --build
```

После запуска приложение доступно по адресу <http://localhost:8000/>. База SQLite хранится в именованном Docker-томе `task_data` и не пропадает при пересоздании контейнера.

Остановка:

```bash
docker compose down
```

## Локальный запуск без Docker

Создайте виртуальное окружение, активируйте его и установите зависимости:

```bash
python -m venv .venv
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

Виртуальное окружение и локальная база исключены из Git.

## Проверка и тесты

```bash
python manage.py check
python manage.py test
```

## Администратор и тестовые данные

Суперпользователь создаётся локально или непосредственно на сервере — его пароль нельзя хранить в репозитории:

```bash
python manage.py createsuperuser
```

После этого административная панель доступна по адресу `/admin/`. Тестовые задачи можно создать через панель либо через обычный интерфейс. Для проверки разделения данных зарегистрируйте двух пользователей.

## Переменные окружения

Скопируйте `.env.example` в `.env` для ориентира. Django не читает `.env` автоматически: при локальном запуске задайте переменные в оболочке, а при Docker-запуске они уже описаны в `compose.yaml`.

| Переменная | Назначение |
| --- | --- |
| `DJANGO_SECRET_KEY` | Секретный ключ, обязателен при `DJANGO_DEBUG=False` |
| `DJANGO_DEBUG` | `True` только для локальной разработки |
| `DJANGO_ALLOWED_HOSTS` | Разрешённые имена хостов через запятую |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Доверенные HTTPS-источники через запятую |
| `DATABASE_URL` | Подключение PostgreSQL; если не задано, используется SQLite |
| `SQLITE_PATH` | Необязательный путь к SQLite-файлу |
| `DJANGO_SECURE_HSTS_SECONDS` | Срок HSTS в production; по умолчанию 31536000 секунд |

## Развёртывание на Render

В корне репозитория находится `render.yaml`, описывающий бесплатный веб-сервис. При создании Blueprint в Render:

1. Подключите репозиторий и выберите `render.yaml`.
2. Укажите `DATABASE_URL` от PostgreSQL-сервиса. Не добавляйте это значение в GitHub.
3. Render автоматически создаст секретный ключ, установит зависимости, применит миграции и запустит Gunicorn.
4. После успешной сборки приложение откроется по HTTPS-адресу вида `https://rksi-task-manager.onrender.com`.

Для учебной проверки можно использовать бесплатную внешнюю PostgreSQL-базу. SQLite на бесплатном Render не подходит для постоянных данных: файловая система сервиса очищается при перезапуске.

## Состав проекта

- `task_manager` — настройки и основные маршруты Django;
- `tasks` — модель `Task`, форма, представления, маршруты, админка и тесты;
- `users` — регистрация и маршруты аутентификации;
- `templates` и `static` — шаблоны Bootstrap 4 и оформление;
- `compose.yaml` и `Dockerfile` — воспроизводимый контейнерный запуск;
- `render.yaml` — конфигурация интернет-развёртывания.

Секреты, пароли, рабочие базы, виртуальное окружение и реальные пользовательские данные не должны добавляться в репозиторий.
